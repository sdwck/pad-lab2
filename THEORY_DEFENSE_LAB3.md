# Вопросы и ответы к защите: Docker и Kubernetes

## 1. В чем разница между Docker и виртуальной машиной (VM)?
* **Виртуальная машина (VM):**
  * Работает поверх гипервизора.
  * Запускает полноценную гостевую операционную систему со своим ядром, системными службами и драйверами.
  * Требует гигабайты диска и оперативной памяти, стартует минуты.
* **Контейнер Docker:**
  * Не содержит гостевого ядра, использует общее ядро хоста (Host Kernel).
  * Изоляция реализована на уровне ядра Linux:
    * **Namespaces:** изолируют PID (процессы), NET (сеть, порты), MNT (файловую систему), IPC (межпроцессное взаимодействие), USER (пользователей).
    * **Cgroups (Control Groups):** жестко ограничивают и учитывают потребление ресурсов (CPU, RAM, I/O).
  * Минимальный оверхед: образы весят десятки/сотни мегабайт, старт за доли секунды.

## 2. Почему выбран базовый образ python:3.12-slim?
* Полный образ `python:3.12` весит около 1 ГБ, так как содержит компиляторы (gcc), заголовочные файлы и утилиты отладки. Это увеличивает время скачивания и поверхность атаки (attack surface).
* Образ `python:3.12-slim` весит ~130 МБ: содержит только рантайм Python и glibc. В нем нет лишних бинарников, меньше потенциальных уязвимостей (CVE).
* Почему не Alpine: в Alpine используется `musl libc` вместо `glibc`, из-за чего C-библиотеки Python часто не могут использовать готовые wheels и перекомпилируются при сборке, что замедляет билд и может влиять на стабильность. Debian-slim полностью совместим со стандартными manylinux wheels.

## 3. Зачем запускать приложение не от root (Non-root user)?
* По умолчанию контейнер выполняется от пользователя `root` (UID 0).
* Если злоумышленник сможет эксплуатировать уязвимость приложения и совершить побег из контейнера (container breakout), он получит права root на хостовой машине.
* В Dockerfile создается отдельный непривилегированный пользователь (в проекте `appuser`, UID 10001) и вызывается инструкция `USER appuser`.

## 4. Порядок инструкций и кэширование слоев в Dockerfile
* Docker кэширует каждый промежуточный слой сборки.
* Если скопировать весь код до установки зависимостей:
  ```dockerfile
  COPY . .
  RUN pip install -r requirements.txt
  ```
  любое изменение в коде инвалидирует кэш, и долгая команда `pip install` будет запускаться заново при каждой сборке.
* Правильный порядок:
  ```dockerfile
  COPY requirements.txt .
  RUN pip install --no-cache-dir -r requirements.txt
  COPY . .
  ```
  Зависимости меняются редко, поэтому слой с установленными пакетами берется из кэша. Сборка занимает секунды.

## 5. Зачем нужен файл .dockerignore?
* Исключает ненужные файлы из контекста сборки (build context), который передается демону Docker: `.git`, `__pycache__`, `.venv`, локальные базы данных, тесты, логи.
* Уменьшает объем передаваемых данных, ускоряет сборку и предотвращает случайное попадание локальных конфигураций и секретов в итоговый образ.

## 6. Почему секреты нельзя зашивать в Dockerfile?
* Все директивы `ENV`, `ARG` и промежуточные файлы сохраняются в метаданных слоев образа и доступны для просмотра через `docker history` или `docker save`.
* Секреты (пароли, JWT-ключи, API-токены) должны передаваться исключительно в рантайме: через переменные окружения, Docker Secrets или Kubernetes Secrets.

## 7. Зачем нужен Docker Compose?
* Позволяет описать мультиконтейнерную архитектуру в одном файле `docker-compose.yml` и поднять всю систему одной командой: `docker compose up --build`.
* Создает изолированную сеть между контейнерами, настраивает постоянные тома (volumes) для сохранения данных и определяет зависимости старта (`depends_on`).

## 8. Зачем нужен Kubernetes, если есть Docker?
Docker управляет отдельными контейнерами на одном сервере. Kubernetes управляет распределенным кластером контейнеров и обеспечивает:
1. **Самовосстановление (Self-Healing):** перезапуск упавших контейнеров, вытеснение и перенос подов при сбое ноды.
2. **Горизонтальное масштабирование (Scaling):** изменение количества реплик вручную или автоматически по нагрузке.
3. **Service Discovery и балансировка нагрузки:** стабильный DNS и виртуальный IP для группы подов.
4. **Обновления без простоя (RollingUpdate):** постепенная замена подов старой версии на новые без прерывания обслуживания.

## 9. Базовые сущности Kubernetes
* **Pod (Под):** минимальная единица развертывания в Kubernetes. Содержит один или несколько контейнеров, разделяющих общий сетевой стек (IP, localhost) и дисковые тома. Поды эфемерны: при перезапуске они получают новые IP.
* **Node (Узел):** физический сервер или виртуальная машина, на которой работают поды.
* **Control Plane:**
  * `kube-apiserver` — точка входа для всех запросов управления кластером.
  * `etcd` — распределенное key-value хранилище состояния кластера.
  * `kube-scheduler` — распределяет поды по нодам на основе доступных ресурсов (requests).
  * `kube-controller-manager` — запускает циклы сверки (ReplicaSet, Deployment, Node Controller).

## 10. Что делает Deployment и ReplicaSet?
* **ReplicaSet:** контроллер, который гарантирует, что в кластере запущено ровно заданное количество ($N$) реплик подов определенного шаблона.
* **Deployment:** высокоуровневый контроллер над ReplicaSet. Описывает желаемое состояние приложения, управляет версиями, реализует стратегию обновления `RollingUpdate` и позволяет выполнять откат (`rollout undo`).

## 11. Что делает Service и почему поды не общаются по localhost?
* Поды постоянно пересоздаются и меняют IP-адреса.
* **Service** создает постоянную абстракцию: фиксированный виртуальный IP-адрес (ClusterIP) и доменное имя в кластере (CoreDNS).
* **Почему не localhost:** сетевой стек пода изолирован. Если сервис попытается вызвать `http://localhost:8002`, запрос останется внутри его собственного сетевого пространства имен, где нужный сервис не запущен. Обращение должно идти по DNS-имени сервиса через CoreDNS: `http://catalog-service:8002`.

## 12. Типы сервисов в Kubernetes
* **ClusterIP (по умолчанию):** сервис доступен только внутри кластера. В проекте используется для всех внутренних микросервисов и Redis.
* **NodePort:** открывает статический порт на всех узлах кластера (в диапазоне 30000–32767). Внешний клиент обращается к `<NodeIP>:<NodePort>`. В проекте шлюз открыт на порту 30080.
* **LoadBalancer:** создает внешний балансировщик нагрузки в облачной инфраструктуре (AWS, GCP).
* **Ingress:** HTTP/HTTPS маршрутизатор уровня L7 (маршрутизация по путям `/api/...` и доменам, SSL-сертификаты).

## 13. ConfigMap vs Secret
* Реализуют разделение конфигурации и исполняемого кода (принцип 12-Factor App).
* **ConfigMap:** хранит открытые параметры конфигурации (URL зависимых сервисов, уровень логирования, флаги окружения).
* **Secret:** хранит конфиденциальные данные (JWT-ключи, токены платежных шлюзов, пароли) в кодировке Base64 с защитой от непреднамеренного логирования и ограничением доступа через RBAC.

## 14. Health Checks: LivenessProbe vs ReadinessProbe
* **LivenessProbe (Жизнеспособность):**
  * Проверяет, не завис ли процесс (Deadlock, вечный цикл, утечка памяти).
  * При неудаче: kubelet принудительно завершает контейнер (SIGKILL) и перезапускает его согласно `restartPolicy`.
* **ReadinessProbe (Готовность к трафику):**
  * Проверяет, готов ли контейнер обслуживать запросы клиентов прямо сейчас.
  * При неудаче: контейнер **не перезапускается**, но его IP исключается из Endpoints сервиса, и балансировщик перестает слать на него трафик (например, пока прогревается кэш или загружаются файлы).
* В проекте обе пробы проверяют HTTP эндпоинт `/health`.

## 15. Управление ресурсами: Requests vs Limits
* **Requests (Запросы):**
  * Гарантированный минимум ресурсов (например, 50m CPU, 64Mi RAM).
  * `kube-scheduler` использует requests для поиска ноды: под запустится только на ноде, где физически свободен указанный объем.
* **Limits (Лимиты):**
  * Верхняя граница потребления ресурсов контейнером (например, 300m CPU, 256Mi RAM).
  * При превышении CPU: процесс не завершается, включается троттлинг (CPU Throttling — ядро выделяет меньше процессорных тактов).
  * При превышении памяти: ядро Linux немедленно убивает контейнер с ошибкой `OOMKilled` (Exit Code 137).

## 16. PersistentVolumeClaim (PVC)
* Контейнеры эфемерны: любые файлы, записанные внутри контейнера, теряются при пересоздании пода.
* **PVC (`pad-data-pvc`):** декларативный запрос на выделение постоянного дискового пространства (1Gi).
* Том монтируется в путь `/data` стейтфул-микросервисов с параметром `subPath`, сохраняя JSON-файлы данных при перезапусках.

## 17. Как работает самовосстановление (Self-Healing)?
1. Выполняется удаление пода: `kubectl delete pod order-service-xxx -n pad`.
2. Контроллер ReplicaSet в непрерывном цикле сверки (Reconciliation Loop) фиксирует расхождение: фактическое количество подов (1) меньше желаемого (2).
3. ReplicaSet немедленно запрашивает у `kube-apiserver` создание нового пода.
4. `kube-scheduler` назначает ноду, `kubelet` стартует контейнер, проверяет liveness и readiness пробы.
5. Новый под вводится в пул сервиса. Восстановление занимает 1–3 секунды без простоя сервиса (Zero Downtime).

## 18. Основные команды для демонстрации

| Действие | Команда | Назначение |
|---|---|---|
| Показать все поды | `kubectl get pods -n pad -o wide` | Проверка статуса Running, 1/1 Ready, 0 рестартов. |
| Показать сервисы | `kubectl get svc -n pad` | Проверка 13 ClusterIP сервисов и 1 NodePort (:30080). |
| Показать развертывания | `kubectl get deployments -n pad` | Проверка числа реплик (по 2 у catalog и order). |
| Показать логи пода | `kubectl logs <pod-name> -n pad --tail=20` | Логи uvicorn, успешные ответы 200 на `/health`. |
| Масштабирование | `kubectl scale deployment order-service --replicas=4 -n pad` | Увеличение реплик до 4 и распределение трафика. |
| Самовосстановление | `kubectl delete pod <pod-name> -n pad` | Удаление пода и наблюдение за автоматическим пересозданием. |
| Проверка API | `curl http://localhost/api/catalog/products` | Проверка проксирования через шлюз по CoreDNS. |
