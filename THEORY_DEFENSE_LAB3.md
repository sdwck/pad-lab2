## БЛОК 1. DOCKER И КОНТЕЙНЕРИЗАЦИЯ

### 1.1. Чем Docker отличается от виртуальной машины (VM)?
* **Виртуальная машина (VM):**
  * Работает поверх гипервизора (Type 1 или Type 2).
  * Внутри каждой VM запускается **полноценная гостевая ОС (Guest OS)** со своим ядром, системными демонами и драйверами.
  * Высокий оверхед: гигабайты диска и ОЗУ на каждую VM, долгий запуск (минуты).
* **Контейнер Docker:**
  * Не содержит гостевого ядра. Все контейнеры делят **одно общее ядро хоста (Host Linux Kernel)**.
  * Изоляция на уровне ядра Linux через:
    * `Namespaces`: изолируют PID (процессы), NET (сетевые интерфейсы и порты), MNT (файловую систему), IPC (межпроцессное взаимодействие), UTS (хостнейм), USER (пользователей).
    * `Cgroups` (Control Groups): жестко лимитируют и учитывают потребление ресурсов (CPU, RAM, I/O).
  * Минимальный оверхед: образ весит десятки/сотни МБ, запуск за миллисекунды.

### 1.2. Базовый образ: почему `python:3.12-slim`?
* Образ `python:3.12` (полный) весит ~1 ГБ (содержит компиляторы gcc, утилиты отладки, библиотеки сборки).
* Образ `python:3.12-slim` весит ~130 МБ:
  * Включает минимально необходимый рантайм Python и libc.
  * Уменьшает время скачивания и развертывания в кластере.
  * Минимизирует поверхность атаки (**Attack Surface**): нет лишних бинарников, меньше уязвимостей (CVE).
* Почему не `alpine`? В Alpine используется `musl libc` вместо `glibc`, из-за чего многие wheel-пакеты C-расширений Python перекомпилируются при сборке и работают медленнее. `slim` (на базе Debian) гарантирует нативную совместимость с `manylinux` wheels.

### 1.3. Принцип наименьших привилегий (Non-root user)
* По умолчанию Docker выполняет команды от пользователя `root` (UID 0).
* В production запуск от root категорически запрещен:
  * При побеге из контейнера (container breakout) через уязвимость ядра злоумышленник получает права суперпользователя на хост-ноде.
* Решение:
  ```dockerfile
  RUN addgroup --system --gid 10001 appgroup && \
      adduser --system --uid 10001 --ingroup appgroup --no-create-home appuser
  USER appuser
  ```
  Приложение изолировано внутри непривилегированного контекста UID 10001.

### 1.4. Кэширование слоев при сборке (Layer Caching)
* Docker выполняет сборку построчно: каждый шаг создает неизменяемый слой (layer).
* Если файлы шага не изменились, Docker берет слой из кэша.
* Неправильный порядок:
  ```dockerfile
  COPY . .
  RUN pip install -r requirements.txt
  ```
  При любом изменении одной строчки кода кэш инвалидируется, и `pip install` запускается заново (долгий билд).
* Правильный порядок (применен в проекте):
  ```dockerfile
  COPY requirements.txt .
  RUN pip install --no-cache-dir -r requirements.txt
  COPY . .
  ```
  Зависимости меняются редко $\rightarrow$ слой с установленными пакетами всегда берется из кэша. Билд занимает 2 секунды.

### 1.5. Файл `.dockerignore`
* Исключает файлы из контекста сборки (build context), отправляемого демону Docker.
* Исключаются: `.git/`, `.venv/`, `__pycache__/`, `*.log`, локальные БД `*.json`, тесты.
* Зачем: ускоряет отправку контекста, снижает размер образа, предотвращает утечку секретов и локальных конфигов в образ.

### 1.6. Секреты в Docker-образе
* Пароли, JWT-ключи и токены нельзя передавать через `ARG`, `ENV` в Dockerfile или зашивать в файлы внутри образа.
* Все слои образа доступны для инспекции (`docker history`, `docker save`). Секреты навсегда остаются в истории слоев.
* Секреты должны передаваться исключительно **на этапе рантайма** через переменные окружения, Docker Secrets или Kubernetes Secrets.

### 1.7. Docker Compose
* Инструмент декларативного управления мультиконтейнерными приложениями на одном хосте.
* В проекте поднимает 14 контейнеров одной командой:
  * Изолированная виртуальная сеть (`bridge network`).
  * Межсервисный DNS по именам сервисов (`http://catalog-service:8002`).
  * Постоянный том `pad_data` для персистентности данных между перезапусками.
  * Управление порядком старта через `depends_on`.

## БЛОК 2. АРХИТЕКТУРА KUBERNETES

### 2.1. Зачем нужен Kubernetes, если есть Docker?
Docker работает на одном сервере и не управляет жизненным циклом при авариях. Kubernetes решает задачи распределенного кластера:
1. **Self-Healing:** Автоматический перезапуск упавших контейнеров и их перенос при отказе физического сервера.
2. **Auto-scaling:** Автоматическое горизонтальное масштабирование количества реплик по нагрузке.
3. **Service Discovery & Load Balancing:** Единая точка входа с внутренним DNS и балансировкой трафика между репликами.
4. **Zero-downtime Rollouts:** Постепенное обновление версий (RollingUpdate) без остановки обслуживания клиентов.

### 2.2. Основные сущности кластера
* **Pod (Под):** Минимальная атомарная единица развертывания в K8s. Содержит один или несколько тесно связанных контейнеров, делящих общий сетевой стек (IP, порты, localhost) и тома хранения.
* **Node (Узел):** Физический или виртуальный сервер кластера (содержит kubelet, kube-proxy, container runtime).
* **Control Plane (Управляющий слой):**
  * `kube-apiserver` — единая точка входа для всех запросов (REST API).
  * `etcd` — распределенное key-value хранилище состояния кластера.
  * `kube-scheduler` — распределяет поды по нодам на основе доступных ресурсов.
  * `kube-controller-manager` — запускает контроллеры (Node, Deployment, ReplicaSet).

### 2.3. Что такое Deployment и ReplicaSet?
* **ReplicaSet:** Низкоуровневый контроллер, гарантирующий, что в кластере в любой момент времени запущено ровно $N$ экземпляров подов заданного шаблона.
* **Deployment:** Высокоуровневый декларативный контроллер над ReplicaSet.
  * Управляет версиями приложения.
  * Обеспечивает стратегию обновления **RollingUpdate**: создает новый ReplicaSet, поднимает поды новой версии по одному, ждет прохождения readinessProbe, затем гасит старые поды.
  * Позволяет мгновенно выполнить откат версии (`kubectl rollout undo`).

### 2.4. Kubernetes Service и межсервисная маршрутизация
* Поды эфемерны: при падении или масштабировании старый под уничтожается, создается новый с **новым IP-адресом**.
* **Service** — абстракция, предоставляющая стабильный виртуальный IP (ClusterIP) и постоянное DNS-имя в кластере.
* **Почему сервисы НЕ должны обращаться через `localhost`?**
  * `localhost` замкнут внутри сетевого пространства имен конкретного пода. Если `order-service` сделает запрос на `http://localhost:8002`, он обратится к самому себе, где каталога нет.
  * В K8s обращение идет через внутренний CoreDNS: `http://catalog-service:8002`.
  * Демон `kube-proxy` на ноде перехватывает трафик к ClusterIP и транслирует его через iptables/IPVS на реальные IP-адреса живых подов-реплик, балансируя нагрузку.

### 2.5. Типы сервисов (Service Types)
* **ClusterIP (по умолчанию):** Сервис доступен только внутри кластера. В проекте используется для всех 12 микросервисов и Redis.
* **NodePort:** Открывает статический порт (диапазон 30000–32767) на всех нодах кластера. Внешний трафик перенаправляется на сервис. В проекте порт `:30080` выделен для API Gateway.
* **LoadBalancer:** Интегрируется с облачным провайдером (AWS, GCP, Azure) и создает внешний аппаратный балансировщик с публичным белым IP.
* **Ingress:** Маршрутизатор уровня L7 (HTTP/HTTPS) с маршрутизацией по путям и доменам, SSL-терминацией.

## БЛОК 3. КОНФИГУРАЦИЯ, НАДЕЖНОСТЬ И РЕСУРСЫ

### 3.1. ConfigMap vs Secret
* Следуют III фактору методологии **12-Factor App**: строгая изоляция конфигурации от кода.
* **ConfigMap:** Хранит несекретные параметры (URL сервисов, уровни логирования `INFO`, таймауты).
* **Secret:** Хранит конфиденциальные данные (JWT-ключи, API-токены платежного шлюза, пароли).
  * Данные кодируются в Base64.
  * В etcd могут шифроваться в покое (encryption at rest).
  * Монтируются в поды только тем сервисам, которым разрешен RBAC-доступ.
  * Не выводятся в чистом виде при стандартном логировании.

### 3.2. Health Checks: LivenessProbe vs ReadinessProbe
* **LivenessProbe (Проверка жизнеспособности):**
  * Вопрос: *"Процесс жив или завис в deadlock/OOM?"*
  * Если проверка не проходит `failureThreshold` раз (например, 3 раза по 15 сек): Kubelet принудительно убивает контейнер (SIGKILL) и перезапускает его.
* **ReadinessProbe (Проверка готовности к трафику):**
  * Вопрос: *"Готов ли контейнер принимать трафик прямо сейчас?"*
  * Если проверка не проходит: контейнер **не убивается**, но его IP-адрес исключается из списка активных Endpoints сервиса. Балансировщик перестает направлять на него запросы клиентов (например, пока прогревается кэш или загружаются данные).
* В проекте обе пробы настроены по протоколу HTTP на эндпоинт `/health` каждого сервиса.

### 3.3. Ресурсы: Requests vs Limits
* **Requests (Запросы):**
  * Гарантированный минимум ресурсов (например, `cpu: 50m`, `memory: 64Mi`).
  * Используются планировщиком `kube-scheduler` при выборе ноды: если на ноде нет свободного объема requests, под туда не запланируется.
* **Limits (Лимиты):**
  * Максимально допустимый потолок потребления (например, `cpu: 300m`, `memory: 256Mi`).
  * **Превышение CPU:** Процесс не убивается, но подвергается троттлингу (CPU Throttling — ядро выделяет меньше тактов CFS).
  * **Превышение Memory:** Контейнер немедленно убивается ядром Linux с кодом ошибки `OOMKilled` (Exit Code 137).

### 3.4. Персистентность данных: PersistentVolumeClaim (PVC)
* Контейнеры и поды эфемерны: при рестарте все локальные файлы в контейнере удаляются.
* **PVC (`pad-data-pvc`):** Декларативный запрос на выделение постоянного дискового хранилища (1Gi).
* Том монтируется в путь `/data` стейтфул-сервисов (`order`, `catalog`, `auth`, `payment` и т.д.).
* Опция `subPath: <service_name>` изолирует каталоги сервисов внутри общего тома без конфликта имен файлов.

## БЛОК 4. САМОВОССТАНОВЛЕНИЕ, МАСШТАБИРОВАНИЕ И КОМАНДЫ ЗАЩИТЫ

### 4.1. Как работает Self-Healing (Самовосстановление)?
1. Администратор или авария уничтожает под: `kubectl delete pod order-service-xxx -n pad`.
2. Контроллер ReplicaSet работает в непрерывном цикле сверки (**Reconciliation Loop**):
   $$\text{Desired State (2)} \ne \text{Current State (1)}$$
3. ReplicaSet немедленно отправляет команду `kube-apiserver` на создание нового пода.
4. `kube-scheduler` находит подходящую ноду.
5. `kubelet` запускает контейнер, проверяет liveness/readiness пробы.
6. Под добавляется в пул сервиса. Время восстановления — 1–3 секунды. Простоев в обслуживании нет (**Zero Downtime**).

### 4.2. Как работает масштабирование (Scaling)?
* Горизонтальное масштабирование (HPA / Scale):
  ```bash
  kubectl scale deployment order-service --replicas=4 -n pad
  ```
* Контроллер Deployment меняет `desired replicas = 4`.
* ReplicaSet поднимает 2 новых пода параллельно.
* Как только они проходят `readinessProbe`, трафик начинает автоматически балансироваться на все 4 экземпляра (Round-Robin через kube-proxy).

### 4.3. Обязательные команды для демонстрации преподавателю

| Действие | Команда | Что показать/объяснить |
|---|---|---|
| 1. Показать все поды | `kubectl get pods -n pad -o wide` | Все 14–17 подов в статусе `Running`, 1/1 Ready, 0 рестартов, разные IP. |
| 2. Показать сервисы | `kubectl get svc -n pad` | 13 ClusterIP сервисов с внутренними IP и 1 NodePort (:30080). |
