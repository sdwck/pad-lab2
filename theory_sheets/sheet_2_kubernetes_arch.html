1. Зачем нужен Kubernetes, если есть Docker?

Docker запускает изолированные контейнеры на одном хосте. В распределенных системах Kubernetes берет на себя оркестрацию кластера:

  • Self-Healing: автоматический перезапуск упавших контейнеров и перенос на здоровые ноды.
  • Auto-scaling: горизонтальное масштабирование количества реплик по нагрузке.
  • Service Discovery & Load Balancing: единый виртуальный IP и DNS с балансировкой трафика.
  • Zero-downtime Rollouts: бесшовное обновление версий (RollingUpdate) без остановки системы.

2. Базовые сущности: Pod, Node, Control Plane

  • Pod (Под): минимальная единица развертывания. Группа из 1+ контейнеров, делящих общий сетевой стек (IP, localhost) и тома. Поды эфемерны: их IP меняются при перезапуске.
  • Node (Узел): рабочий сервер кластера (компоненты: kubelet, kube-proxy, CRI runtime).
  • Control Plane:
    • kube-apiserver — центральный REST API кластера, через него общаются все компоненты.
    • etcd — отказоустойчивое key-value хранилище состояния всего кластера.
    • kube-scheduler — выбирает узел для размещения пода с учетом CPU/RAM requests.
    • kube-controller-manager — запускает контроллеры сверки (Node, Deployment, ReplicaSet).

3. Deployment и ReplicaSet

  • ReplicaSet: гарантирует, что в кластере работает строго заданное число реплик ($N$) подов.
  • Deployment: декларативное описание желаемого состояния над ReplicaSet.
    • Обеспечивает обновление RollingUpdate: создает новый ReplicaSet, поднимает новые поды по одному, дожидается их готовности (readinessProbe), после чего гасит старые.
    • Обеспечивает откат версий (kubectl rollout undo).
  • High Availability в проекте: для order-service и catalog-service сразу задано replicas: 2 для исключения единой точки отказа (SPOF).

4. Kubernetes Service и CoreDNS: почему НЕ localhost?

Почему сервисы не могут обращаться по localhost?

Сетевой стек пода строго изолирован. localhost указывает на собственный контейнер пода. Запрос от order-service на http://localhost:8002 вернет ошибку Connection Refused, так как каталог работает в отдельном поде со своим сетевым пространством имен.

  • Решение: сущность Service предоставляет постоянный виртуальный IP (ClusterIP) и стабильное DNS-имя в кластере (CoreDNS).
  • Вызов внутри кластера: http://catalog-service:8002. Служба kube-proxy перехватывает обращение к ClusterIP и транслирует его на реальные IP-адреса живых подов-реплик через iptables/IPVS.
